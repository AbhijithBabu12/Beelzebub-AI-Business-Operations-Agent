# 1. Architectural Overview

Beelzebub will use a **modular monolithic architecture** with a React frontend, FastAPI backend, PostgreSQL database, and a stateful AI workflow orchestration layer.

The application will be structured into independent logical modules with clearly defined responsibilities.

The initial system will be deployed as a small number of independently runnable components rather than a distributed microservice architecture.

## 1.1 Architectural Goals

The architecture must:

1. Separate presentation, business logic, data access, and AI orchestration.
2. Ensure PostgreSQL remains the source of truth for business information.
3. Prevent LLMs from directly modifying authoritative business records.
4. Support controlled multi-step agent workflows.
5. Support human approval and workflow interruption.
6. Prevent duplicate consequential operations.
7. Preserve workflow and audit history.
8. Support future multi-business deployment.
9. Remain straightforward to develop, test, and deploy.

## 1.2 Architecture Style

Selected architecture: Modular Monolith.

Reasons:

- Easier local development.
- Simpler deployment.
- Lower infrastructure overhead.
- Easier transaction management.
- Clear separation of application responsibilities.
- Avoids premature distributed-system complexity.

Individual modules may be extracted into separate services in the future if justified by actual requirements.

# 2. High-Level Architecture

The system consists of the following components:

1. Frontend application.
2. API and authentication layer.
3. Business service layer.
4. Database access layer.
5. AI orchestration layer.
6. Validated tool layer.
7. Approval management layer.
8. Audit logging layer.
9. PostgreSQL database.

## 2.1 Frontend

Technology:

- React
- Vite
- TypeScript
- Tailwind CSS

Responsibilities:

- Display the business dashboard.
- Display inventory information.
- Display supplier information.
- Display purchase orders.
- Display pending approvals.
- Display invoice information.
- Provide the AI assistant interface.
- Display workflow execution progress.
- Present errors and recovery options.

The frontend must never be trusted to enforce business authorization.

All security-sensitive operations must be validated by the backend.

## 2.2 API Layer

Technology: FastAPI.

Responsibilities:

- Expose REST endpoints.
- Authenticate users.
- Enforce business-level authorization.
- Validate request payloads.
- Invoke business services.
- Invoke agent workflows.
- Return structured responses.
- Handle API errors consistently.

The API layer acts as the entry point for all frontend requests.

## 2.3 Business Service Layer

Responsibilities:

- Inventory calculations.
- Low-stock detection.
- Reorder quantity calculation.
- Supplier eligibility.
- Supplier comparison.
- Purchase order preparation.
- Invoice calculations.
- Overdue invoice detection.
- Daily operational summaries.

Business rules must be implemented in deterministic Python functions.

The LLM must not independently calculate or determine authoritative business values.

## 2.4 Database Access Layer

Technology:

- SQLAlchemy
- PostgreSQL
- Alembic

Responsibilities:

- Manage database connections.
- Execute controlled database operations.
- Manage transactions.
- Retrieve business records.
- Persist application state.
- Enforce data integrity.
- Apply schema migrations.

Database access should be performed through controlled repositories or service functions rather than arbitrary SQL generated by an LLM.

## 2.5 AI Orchestration Layer

Technology: LangGraph.

Responsibilities:

- Interpret user requests.
- Determine appropriate workflows.
- Coordinate validated tools.
- Maintain workflow state.
- Handle bounded retries.
- Pause for human approval.
- Resume interrupted workflows.
- Produce structured explanations.

The orchestrator coordinates business operations but does not own authoritative business data.

The LLM is responsible for language understanding, tool coordination, and explanation.

Python services and PostgreSQL remain responsible for business facts and decisions.

## 2.6 Tool Layer

The tool layer exposes validated application capabilities to the AI orchestrator.

Initial tools:

- get_inventory_summary
- detect_low_stock
- calculate_reorder_quantity
- get_supplier_options
- compare_suppliers
- create_purchase_order_draft
- get_overdue_invoices
- draft_customer_reminder
- generate_daily_briefing

Each tool must have:

- Input schema.
- Output schema.
- Permission requirements.
- Validation rules.
- Error-handling policy.
- Execution timeout.

Tools must call application services rather than directly implementing separate business rules.

## 2.7 Approval Management Layer

Responsibilities:

- Create approval requests.
- Associate approvals with specific business actions.
- Validate approver permissions.
- Record approval and rejection decisions.
- Detect changes to previously reviewed actions.
- Require renewed approval when consequential details change.
- Prevent repeated execution.

Approval validation must happen on the backend.

A LangGraph interrupt alone is not an authorization mechanism.

## 2.8 Audit Logging Layer

Responsibilities:

- Record consequential business actions.
- Record approval decisions.
- Record purchase order state transitions.
- Record relevant workflow failures.
- Maintain timestamps and actor information.
- Preserve references to affected records.

Audit history must not depend solely on LLM-generated descriptions.

# 3. Application Request Flow

## 3.1 Normal Business Request

Example:

A user requests an inventory summary.

Flow:

1. Frontend sends an authenticated API request.
2. FastAPI validates the user.
3. Backend verifies business-level access.
4. Inventory service retrieves authorized records.
5. Business logic calculates the summary.
6. API returns structured results.
7. Frontend displays the information.

No LLM is necessary for this deterministic operation.

## 3.2 AI-Assisted Request

Example:

"Check which products need reordering and prepare purchase orders."

Flow:

1. User submits a natural-language request.
2. API authenticates the user and checks business access.
3. API creates or resumes an agent workflow.
4. LangGraph interprets the requested task.
5. Agent selects appropriate validated tools.
6. Tools retrieve inventory and supplier information.
7. Business services calculate reorder quantities.
8. Supplier comparison services evaluate eligible options.
9. Purchase order drafts are prepared.
10. Agent generates an explanation grounded in the results.
11. Workflow pauses for approval.
12. Frontend displays the proposed purchase orders.
13. Authorized user reviews the proposal.
14. Backend validates the approval against the reviewed order version.
15. Purchase order state is updated transactionally.
16. Audit events are recorded.
17. Workflow returns its final status.

The agent must not bypass the approval service.

# 4. Purchase Order Approval Architecture

Purchase order approval is a critical security boundary.

## 4.1 Purchase Order Lifecycle

Initial states:

- DRAFT
- PENDING_APPROVAL
- APPROVED
- REJECTED
- CANCELLED
- EXPIRED
- REQUIRES_REVIEW
- RECORDED

Allowed transitions must be explicitly implemented and tested.

## 4.2 Approval Integrity

Every approval request must reference a specific purchase order version.

The system should maintain an immutable snapshot or equivalent canonical representation of the reviewed purchase order.

The approval must be valid only for the exact reviewed version.

If consequential details change:

1. Invalidate the existing approval.
2. Mark the purchase order as requiring review.
3. Generate a new reviewable version.
4. Obtain fresh authorization.

## 4.3 Transaction Safety

The backend must validate and record an approval within an appropriate database transaction.

Use database constraints and idempotency controls to prevent duplicate actions.

A repeated request must not create multiple purchase orders or repeat an already completed consequential operation.

# 5. Database Architecture

PostgreSQL is the authoritative persistence layer.

Initial logical entity groups:

## Business and Access

- businesses
- users
- business_memberships
- roles or permissions

## Inventory

- products
- product_categories
- inventory_locations
- inventory_stock
- inventory_movements

## Suppliers

- suppliers
- supplier_products

## Purchasing

- purchase_orders
- purchase_order_items
- approval_requests
- approval_decisions

## Customers and Invoices

- customers
- invoices
- invoice_payments

## Agent and Audit

- workflows
- workflow_events
- audit_logs

These are logical entities, not finalized SQLAlchemy models.

The detailed schema, constraints, indexes, and relationships will be defined in DATABASE_DESIGN.md.

## 5.1 Data Isolation

Every business-owned record must be associated with the appropriate business.

Queries must enforce business-level authorization.

The backend must not rely on frontend filtering to protect business data.

Cross-business access must be covered by automated tests.

# 6. Agent Workflow Architecture

LangGraph will manage stateful operational workflows.

## 6.1 Central Orchestrator

Initially, Beelzebub will use one central orchestrator.

The orchestrator will:

1. Interpret the user request.
2. Determine the relevant operation.
3. Select validated tools.
4. Coordinate execution.
5. Handle recoverable failures.
6. Pause for approval when required.
7. Resume after approval or rejection.
8. Produce a final explanation.

We will not introduce multiple autonomous agents in the initial version.

## 6.2 Workflow State

Important workflow information should be persisted.

Initial state fields may include:

- workflow_id
- business_id
- user_id
- request
- workflow_type
- current_step
- status
- tool_results
- proposed_actions
- approval_reference
- error_details
- created_at
- updated_at

The final state schema will be implemented with typed validation.

## 6.3 Persistence and Recovery

LangGraph checkpointing will support workflow continuation.

PostgreSQL will be used for persistent application data and, where appropriate, workflow checkpoint storage.

The selected checkpointing implementation must be tested for restart recovery and approval resumption.

## 6.4 Retry and Timeout Policy

- Tool calls must have defined timeouts.
- Retries must be bounded.
- Validation failures must not be retried blindly.
- Non-idempotent operations must use idempotency protection.
- Failed workflows must expose useful error information.
- Unrecoverable failures must stop safely.

# 7. Security Architecture

Security is enforced by the backend, not by agent prompts.

## 7.1 Authentication

Users must authenticate before accessing private business data.

The authentication implementation will be selected during backend development.

## 7.2 Authorization

The backend must check:

- User identity.
- Business membership.
- Role and permissions.
- Action-specific authorization.

## 7.3 LLM Security

The LLM must never:

- Generate executable SQL for direct execution.
- Directly modify authoritative database records.
- Override user permissions.
- Approve its own proposed actions.
- Bypass application validation.

Tool inputs and outputs must be validated.

## 7.4 Untrusted Content

External documents, uploaded files, supplier messages, and email content must be treated as untrusted data.

Their contents must never override application instructions or permissions.

## 7.5 Secrets

- API credentials must be stored in environment configuration or an appropriate secrets manager.
- Real credentials must never be committed to Git.
- `.env` files must be excluded from version control.
- Production credentials must be separate from development credentials.

---

# 8. Error Handling and Observability

The application must use structured logging.

Important events include:

- API request failures.
- Database errors.
- Tool execution failures.
- Workflow interruptions.
- Approval decisions.
- Purchase order state changes.
- Retry attempts.
- Authorization failures.

Sensitive information and secrets must not be written to logs.

Errors returned to users should be understandable without exposing internal stack traces or confidential information.

# 9. Deployment Architecture

## 9.1 Local Development

Initial local development:

- React frontend running through Vite.
- FastAPI backend running through Uvicorn.
- PostgreSQL running through Docker Compose.
- Python virtual environment for backend dependencies.

## 9.2 Production Deployment

Proposed production components:

- Hosted React frontend.
- Hosted FastAPI backend.
- Managed PostgreSQL database.
- Secure environment configuration.
- HTTPS.
- Appropriate backup and recovery strategy.

Docker will provide reproducible application environments.

The hosting provider and deployment topology will be selected after the local MVP is working.

## 9.3 No Premature Infrastructure

The initial version will not require:

- Kubernetes.
- Microservices.
- Dedicated message brokers.
- Multiple databases.
- Vector databases.
- Distributed agent services.

Additional infrastructure requires a documented technical justification.

# 12. Architectural Decisions

| Decision | Selection | Reason |
|---|---|---|
| Architecture | Modular monolith | Simpler and maintainable MVP |
| Frontend | React + Vite | Responsive business interface |
| Backend | FastAPI | Typed Python API |
| Validation | Pydantic | Structured contracts |
| ORM | SQLAlchemy | Controlled database operations |
| Database | PostgreSQL | Reliable relational storage |
| Migrations | Alembic | Version-controlled schema evolution |
| Agent orchestration | LangGraph | Stateful workflows and approval interruptions |
| Business logic | Deterministic Python | Reliable business calculations |
| Testing | pytest | Automated verification |
| Deployment | Docker | Reproducible environments |

Any significant changes must be documented in DECISIONS.md.

# 13. Architectural Quality Requirements

The architecture is considered correctly implemented only when:

- The frontend communicates through validated APIs.
- Business calculations work independently of the LLM.
- Database records remain authoritative.
- Business-level authorization is enforced.
- Agent tools use controlled application services.
- Purchase order approvals cannot be bypassed.
- Modified proposals require renewed approval.
- Workflow state can be recovered.
- Duplicate actions are prevented.
- Consequential operations are audited.
- Automated tests verify the important guarantees.

- Additional business workflows.
- More sophisticated scheduling.

# 15. Final Architecture Statement

Beelzebub is designed as a modular business operations platform with an AI orchestration layer.

Its intelligence comes from combining:

- Authoritative business data.
- Deterministic application logic.
- Validated tools.
- Stateful workflow orchestration.
- Explicit human authorization.
- Persistent execution history.
- Auditable business actions.

The AI agent coordinates the work. The application enforces the rules. The database preserves the truth.

**Architecture principle: Intelligent coordination, deterministic execution, and human-controlled actions.**
